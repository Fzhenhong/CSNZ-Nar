# CSNZ-Nar解包打包工具-By：大宏

重新实现的 CSOL / CSNZ NAR 归档工具，一体化支持**解包**与**打包**。
针对旧工具的两个核心缺陷重写：旧工具把整份归档读进内存，2 GB 级别的
文件会内存不足、解压中断；本工具全程流式处理，实测 2 GB 归档峰值内存约 42 MB。

## 直接使用

| 文件 | 说明 |
|---|---|
| `CSNZ-Nar.exe` | 图形界面，双击即用（自包含，无需安装 .NET） |
| `命令行\nar.exe` | 命令行版本，适合批处理与脚本 |

### 图形界面

窗口分「解包 NAR」和「打包 NAR」两个页签。**两边都只需选目录，其余全自动。**

- **解包**：拖入或选择 .nar → 自动填好输出目录 → 点「开始解包」。
  加密模型会自动解密，并写出 `.nar-info.json` 清单。
- **打包**：选源目录 → 点「开始打包」。归档根、存储方式、模型加密状态
  全部按清单自动还原，不需要任何手工判断。

### 命令行

```
nar list    <归档.nar>                      列出条目
nar extract <归档.nar> <输出目录> [选项]     解包
nar pack    <输入目录> <输出.nar> [选项]      打包
```

解包选项：

| 选项 | 作用 |
|---|---|
| `--threads=<n>` | 并发线程数，默认 CPU 核数一半（2~8） |
| `--no-models` | 不自动解除 .mdl 模型加密（**默认会解**） |
| `--no-manifest` | 不写出 `.nar-info.json` 清单 |
| `--verify` | 解包后按 CRC32 校验，不一致记为失败 |
| `--no-overwrite` | 已存在同名文件时跳过 |
| `--filter=<通配符>` | 只解包匹配的条目，如 `--filter=*.wad` |
| `--root=<路径>` | 只解包该前缀下的条目，如 `--root=/cstrike/models` |

打包选项：

| 选项 | 作用 |
|---|---|
| `--root=<名称>` | 归档内根路径；**留空则沿用清单里的原始路径** |
| `--type=<raw\|enc\|enc+lz>` | 未命中清单时的默认存储方式 |
| `--no-models` | 不还原模型的加密状态 |
| `--no-manifest` | 忽略清单，所有文件统一用 `--type` |

示例（常规用法就是零参数）：

```bat
nar extract data\fixtrike.nar 输出目录
nar pack 输出目录 新的.nar
```

### 自动还原机制

解包时会在输出目录写出 `.nar-info.json`，逐个记录：

- 归档内完整路径（因此打包不必猜 `--root`）
- 原始存储方式（raw / enc / enc+lz，因此不必猜 `--type`）
- 模型原本是否加密、用的是 20 还是 21 号密钥（因此能加密回原样）
- 数据区偏移与目录表序号（用于还原归档布局）

打包时自动向上查找并读取清单（源目录或其上级目录），逐个文件套用。
只有新加的文件（清单里没有）才回退到默认设置。

**实测**：`cstrike.nar`（2 GB / 10853 项）解包后原样打包，产物与原文件
SHA-256 完全相同——即"解包不改文件直接打包"会得到一模一样的归档。

## 实测结果

以 `解包测试fixtrike.nar`（1.47 GB，10996 项）为样本：

| 项目 | 结果 |
|---|---|
| 解包耗时 | 4.2 秒（8 线程，2 GB 归档） |
| 解包峰值内存 | 约 70 MB |
| 打包耗时 | 5.1 秒（并行压缩，2 GB 归档） |
| 重新打包 | 1179.7 MB（原始 1472 MB，含碎片清理） |
| 解包→打包→解包 往返 | 10996 个文件全部字节一致，0 处差异 |
| 2 GB 归档解包峰值内存 | 42 MB（旧工具在此类文件上会内存不足） |
| 原厂 CSOToolLib 兼容性 | 可正常打开新工具生成的归档，10996/10996 项 CRC 通过 |
| `cstrike.nar`（2 GB）往返 | 产物与原文件 **SHA-256 完全相同** |

## 格式说明

NAR 结构（取自对旧工具 CSOToolLib 的逆向，已逐项实测验证）：

```
[0..8)              签名 "NAR\0" + 版本 0x01000000
[8 .. 数据区末)      各条目的存储数据，偏移与长度由目录表给出
目录表              明文 → BZip2 压缩 → 按 16 字节表异或
尾部 8 字节          压缩长度 ^ 0x4076551F + 签名
```

目录表解压后为：版本(1) + 3 个保留字段 + 条目数，随后每个条目：

```
uint16 路径长度 | UTF-8 路径 | int32 存储类型 | uint32 偏移
int32 存储大小 | int32 原始大小 | int32 Unix 时间 | uint32 CRC32
```

三种存储类型：

| 值 | 名称 | 存储形式 |
|---|---|---|
| 0 | 原始 | 明文原样 |
| 1 | 编码 | 明文异或 16 字节路径密钥 |
| 2 | 编码+压缩 | `XOR(LZ77(明文))`，官方归档常用 |

- 条目密钥：Python 风格哈希 `h = h*1000003 ^ byte`，末尾 `h ^= 长度`，
  再用 LCG `h = h*1103515245 + 12345` 取低字节扩展成 16 字节。
- LZ77：8 KB 滑动字典，首字节 `b`，`n = b>>5`、`n2 = b&0x1F`。
  `n=0` 为字面量段（长度 `n2+1`）；`n=1..6` 为匹配段（长度 `n+2`）；
  `n=7` 时再读 1 字节作为长度扩展（长度 `9+额外值`）。距离 `= ((n2<<8)|低位)+1`。
  注意顺序是**先压缩再异或**，写反会让客户端无法读出。
- CRC32：覆盖"最终写出的存储字节"，与客户端 `Verify` 行为一致。

## 一个已知边界

有些官方归档的数据区里残留着"已删除条目"的碎片（例如 `解包测试fixtrike.nar`
有 50 处、约 292 MB）。这些字节不属于任何文件的目录表记录，因此无法还原。

后果：这类归档解包再打包后，条目、路径、内容、压缩方式、模型加密状态
全部一致（`--verify` 全通过），但归档体积会变小（fixtrike 1472 MB → 1179 MB），
整个文件的 SHA-256 不会与原始文件相同。

这属于**清理垃圾**而非损坏。要判断某个归档是否属于这种情况，
打包时的输出会显示清单还原条数与文件大小对比。

## 与旧工具的差异

| 方面 | 旧工具 | 本工具 |
|---|---|---|
| 内存 | 整份归档进内存，大文件失败 | 流式，2 GB 归档约 42 MB |
| 解包速度 | 单线程 | 多线程并发（实测 6.5 秒解完 1.2 GB） |
| 解包/打包 | 两个独立程序 | 一体化，同一界面 |
| 校验 | 需手动点"Verify All" | 可选解包后自动校验 |
| 模型解密 | 独立小工具 | 自动解密，打包时自动加密回原始版本号 |
| 压缩率 | 仅编码不压缩 | 支持 LZ 压缩，输出更小 |
| 出错处理 | 整体中断 | 单文件失败不影响其余，最后汇总报告 |
